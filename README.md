# IMS Tool

Настольное приложение для учёта измерительных приборов на заводе: реестр,
журнал движений и отчёты. Tauri 2 + React 19, база — один файл SQLite на
машине. Сервера у приложения нет.

Приложение отвечает на четыре вопроса, ради которых оно и существует:

1. Где сейчас находится прибор с инвентарным номером N?
2. Что сейчас на руках у сотрудника Иванова?
3. Что происходило с этим прибором за последний год?
4. У каких приборов истекает поверка?

Ни на один из них таблица «текущее состояние» без истории ответить не может,
поэтому журнал операций — центральная сущность, а не побочный лог.

Полный дизайн — [docs/superpowers/specs/2026-09-18-ims-tool-design.md](docs/superpowers/specs/2026-09-18-ims-tool-design.md).

## Принципы

- **Локально.** Данные лежат файлом SQLite в каталоге приложения. Сети,
  сервера и учётных записей нет.
- **Статус меняется только операцией.** Ни форма правки, ни репозиторий не
  дают выставить его напрямую — нельзя «просто поменять статус» и оставить
  прибор числящимся за уволившимся сотрудником.
- **У каждой записи есть автор.** Учётных записей нет, есть подпись: оператор
  один раз вводит ФИО, и оно попадает в каждую запись журнала. Смена имени не
  переписывает прошлое.
- **Ничего не удаляется.** Прибор списывается, справочник архивируется. Журнал
  обязан пережить прибор, иначе система теряет то, ради чего заведена.
- **Числа на экране не расходятся.** Спарклайны плиток считаются по тому же
  журналу, что и сами плитки; «всего» в бублике и «всего» на плитке — одно и
  то же число.
- **Нет мёртвых кнопок.** Недоступная операция не гасится, а отсутствует.

## Запуск

```bash
yarn install
yarn dev            # вёрстка в браузере: http://localhost:1420
yarn tauri dev      # приложение целиком, нужен toolchain Rust
yarn test           # 145 тестов
yarn verify         # типы и тесты одной командой — перед пушем
yarn build          # релизная сборка фронтенда
```

В браузере данными заведует `MemoryRepo`, и при первом открытии сеется витрина:
завод на 48 приборов с историей за полтора месяца — иначе дашборд, графики и
отчёты не на чем смотреть. `?demo=empty` оставляет приложение пустым: так
проверяются первый запуск и окно «Представьтесь».

## Как устроено

```
src/
  app/             тема, роутер, контекст, разметка
  data/            AppRepo, SqliteRepo, MemoryRepo, миграции, контракт
  features/
    instruments/   {domain,ui}
    operations/    переходы состояний, журнал, окна операций
    directories/   справочники
    verification/  поверки
    dashboard/     плитки и графики
    reports/       отчёты
  pages/           экраны
  platform/        окружение, сохранение файлов
  shared/          даты, CSV, результат, страницы
  tour/            обход «Как это работает» и шаги по экранам
```

**Слой данных — порт с двумя реализациями.** `SqliteRepo` работает на
устройстве через `@tauri-apps/plugin-sql`, `MemoryRepo` — в браузере и тестах.
Требования к ним одни и те же и проверяются одним набором `repoContract.ts`:
разные тесты для разных реализаций означали бы, что реализации разъедутся, а
ошибка вылезет на устройстве, где её дороже всего ловить. В тестах драйвером
`SqliteRepo` служит встроенный в Node модуль `node:sqlite`, поэтому по
настоящему движку SQLite гоняется тот же SQL, который пойдёт на устройстве.

**Миграции** — нумерованный массив в `src/data/migrations.ts`, применённая
версия в `PRAGMA user_version`. Миграция, попавшая в сборку, больше никогда не
редактируется: только добавляется новая в конец.

**Переходы состояний** — чистая функция `applyOperation`: ни базы, ни часов
внутри, ни React. Репозиторий только сохраняет её результат одной транзакцией.

## Что нужно знать при доработке

- **Поиск по кириллице идёт по отдельной колонке `search_text`.** Функция
  `lower()` в SQLite знает только латиницу: «Мультиметр» она оставляет как
  есть. Текст приводится к нижнему регистру в приложении и хранится готовым —
  при изменении названия колонку надо пересчитать.
- **У плагина `sql` нет своего API транзакций,** а запросы идут через пул sqlx.
  Все изменяющие операции выстроены в очередь на стороне JS и обёрнуты в
  `BEGIN IMMEDIATE`: пул отдаёт свободное соединение и создаёт новое, только
  когда свободных нет, так что одна запись за раз снимает вопрос.
- **Дизайн-система перенесена из проекта `dashboard-ui`** (шаблон Minimal), но
  без MUI: там она выражена темой MUI, здесь те же значения — палитра,
  типографика, тени, скругления — объявлены переменными CSS в
  `src/ui/tokens.css`. Числа совпадают до последней цифры.
- **Компоненты свои** (`src/ui/`): кнопка, карточка, поля, список, таблица,
  модальное окно, метка, сообщение. Библиотеки интерфейса в зависимостях нет
  вовсе. Диалог сделан на нативном `<dialog>` — он сам переносит фокус внутрь,
  запирает его там и закрывается по Esc; список на обычном `<select>` — он
  работает с клавиатуры и знает про экранные читалки.
- **Таблица своя** (`src/ui/DataTable.tsx`). От прежнего DataGrid нужны были
  шапка, строки, пустое состояние и постраничность, а приезжали сортировка,
  фильтры, виртуализация и локализация, которыми экраны не пользуются.
  Раскладка закреплена (`table-layout: fixed`), длинные названия обрезаются
  многоточием: иначе строки разной высоты, и список нечем читать.
- **Иконки свои** (`src/ui/icons.tsx`), а не Iconify: тот подгружает наборы по
  сети, а приложение работает на заводском ПК, где интернета может не быть.
- **Графики на ApexCharts** — той же библиотеке, что в `dashboard-ui`. Общие
  настройки собраны один раз в `src/ui/Chart.tsx`: тонкие оси, пунктирная
  сетка, градиентная заливка под линией.
- **Цвет означает состояние прибора.** Правило ложится на палитру Minimal без
  натяжек: фирменный зелёный достаётся исправному прибору, бирюзовый
  «информационный» — тому, что на руках, жёлтый предупреждающий — тому, что
  вне строя, красный — тому, что требует действия. Ремонт и поверка выглядят
  одинаково намеренно: цвет несёт тяжесть состояния, причину несёт подпись
  рядом. Те же цвета идут в графики — язык один на весь интерфейс.
- **Моноширинный шрифт только для данных:** инвентарных номеров, серийников,
  дат и чисел в колонках. Цифры одной ширины выстраиваются друг под другом, и
  столбец читается взглядом, а не посимвольно.
- **Обе схемы равноправны,** светлая по умолчанию. Схема живёт атрибутом
  `data-theme` на `<html>`, переменные CSS переключаются сами, выбор
  запоминается. Цвета состояний для схем разные (`useStateColors`): на тёмном
  фоне берутся светлые тона палитры, иначе насыщенный красный перестаёт быть
  сигналом. Хук, а не переменные: цвет уходит в настройки графиков, где
  `var()` не раскрывается.
- **У каждого экрана есть обход «Как это работает»** (`src/tour/`). Шаг
  привязан к элементу атрибутом `data-tour`, а не селектором по классу: класс
  переживает не всякую правку вёрстки и уносит подсказку молча. Шаг, которому
  нечего показать, пропускается — обход не подсвечивает пустоту. Про driver.js
  знает один модуль `startTour.ts`, и он же слушает прокрутку на фазе
  погружения: приложение прокручивается внутри своих контейнеров, а driver.js
  следит только за окном. Подгружается всё это по нажатию — открывают обход
  изредка, а весит он больше любого экрана. Тест сверяет якоря шагов с
  разметкой, поэтому переименованный `data-tour` ломает сборку, а не подсказку.
- **Даты вводятся через `DateInput`,** а не нативным `<input type="date">`:
  нативное поле показывает дату в формате локали системы, и на английской
  Windows кладовщик увидел бы mm/dd/yyyy. Формат задан приложением —
  ДД.ММ.ГГГГ везде.

## Чего пока нет

Ролей и входа · импорта из Excel (схема готова: уникальный инвентарный номер,
источник записи и внешний код строки) · сканера штрихкодов · фотографий
приборов · уведомлений о сроках · печати свидетельств · бронирования · работы
по сети.
